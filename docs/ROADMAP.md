# Mini-FT8 roadmap (kb2slo fork)

Living plan for this fork. How to use it, and the rest of `docs/`, is in [README.md](README.md).

Architecture details stay in `AUTOSEQ_ARCHITECTURE.md` and `AUTOSEQ_INACTIVE_QUEUE.md`. Extract/style/boundaries: [RFC 0002](rfcs/0002-extract-and-boundaries.md). Companion: [RFC 0001](rfcs/0001-ble-companion.md) (Nano UART; phone path not locked, I19). [RFC 0003](rfcs/0003-m32-pocket-port-and-ble-time.md) (Pocket+CTS bundle) is **rejected**. B15 CTS is ROADMAP-only; I17 gets its own RFC if sequenced. Long features get an RFC; this file only points at them.

Ship on `origin/main`. Talk through changes before a local commit (see [README.md](README.md)). Do not open `upstream` PRs unless explicitly asked.

| B23 | USB Drive (`C`) SCSI INQUIRY override is dead code — fix or drop the feature | Bench 2026-09-04: `C` failed to mount on macOS. Operator reports it has always been flaky there and it is **not** a regression from RFC 0002 §5.1 — proven, not assumed: `__wrap_tud_msc_inquiry_cb` is absent from the linked ELF on `main` *and* on the refactor branch, and the two builds' symbol sets are identical. **Verified root cause of the dead override:** TinyUSB declares `tud_msc_inquiry_cb` `TU_ATTR_WEAK` inside `managed_components/espressif__tinyusb/src/class/msc/msc_device.c` and calls it from that same translation unit (line 799). GNU ld's `--wrap` only replaces *undefined* references, so `-Wl,--wrap=tud_msc_inquiry_cb` (now in `main/CMakeLists.txt`, formerly `components/storage_service`) never intercepts it; `--gc-sections` then drops the unreferenced `__wrap_` function at `main/storage_service.cpp:1466`. The definition that actually runs is the **strong** one in `managed_components/espressif__esp_tinyusb/tinyusb_msc.c:1181`, so the ADV advertises itself as `TinyUSB` / `TEST MSC Storage` / `0.1` — never the intended `N6HAN` / `USB DISK` / `1.0` (a stale identity inherited from upstream; not this fork's callsign). Generic INQUIRY strings are a plausible but **unproven** contributor to macOS DiskArbitration flakiness — a lead, not a diagnosis. **Clean fix if kept:** `tud_msc_inquiry2_cb` is weak with no strong competitor anywhere in the tree and TinyUSB calls it *first* (msc_device.c:796), falling back to v1 only on a 0 return — define a strong `tud_msc_inquiry2_cb` and delete both the `--wrap` link option and the dead `__wrap_` function, sidestepping the esp_tinyusb collision entirely. **Or drop USB Drive outright** (operator floated this): SD copy plus the I3/I19 companion paths already cover getting logs off the device. Either way the dead `--wrap` option and dead function should go — shipping a link option and a function that provably never execute is worse than either choice. Decide fix-vs-drop before writing code. Field-only (`C` on a real host). |

| I26 | Decode-depth/sensitivity tuning (ft8_lib) | We run below kgoba's own ft8_lib demo defaults (`components/ft8_lib/vendor/demo/decode_ft8.c`), not just below a skimmer project's tuned numbers: `num_candidates`=50 vs demo default 140 (main.cpp:3004), `freq_osr`=1 vs demo default 2 — no frequency-bin subdivision at all (main.cpp:624). `min_score`=5 and `max_iterations`=25 already match or beat upstream. Two different risk shapes, confirmed 2026-09-03: (a) approaching kgoba's own defaults — `num_candidates` is cheap (stack array, CPU-time cost only, measurable against the ~13s slot budget); `freq_osr` is not (doubles the persistent waterfall buffer, competes with I25's DIRAM budget). (b) The Web-888/RX-888 FT8 skimmer project's published work on this same ft8_lib base (OSD LDPC decoder, frequency-domain subtract-encoded-messages, multi-pass decode) is a real, credibly-documented ~7pt recall improvement over stock ft8_lib (their own recall/precision/F1 table, WSJT-X spots as ground truth) — a real search at the time found no public source to port from (checked `RaspSDR/red-pitaya-notes` and adjacent repos). **Update 2026-09-04:** a likely source since surfaced — `howard0su/ft8_lib`'s commit history (`Substract in each freq_sub`, `Filter out fake signal via message formating check`, same idiosyncratic misspellings as the rx-888.com writeup) and stated target (`Zynq7010 with 2 ARM cores`, Web-888's own hardware) match closely enough to be very likely the same work, though not explicitly confirmed by either party — worth a real look before assuming reimplementation-from-description is still necessary. OSD specifically is a materially heavier LDPC path that may not fit our IRAM/DIRAM budget at all regardless of source availability. Needs a decode-recall bench harness (recorded audio + known-truth spots, Web-888's own methodology) before any of this is sequenced — that harness is likely the actual first Backlog-worthy step, not the algorithm changes themselves. See I24's 2026-09-04 update for a possible future PSRAM-rich host (ESP32-P4) that would remove this ceiling entirely, independent of any algorithm work here. |
