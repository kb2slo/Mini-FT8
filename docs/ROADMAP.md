# Mini-FT8 roadmap (kb2slo fork)

Living plan for this fork. How to use it, and the rest of `docs/`, is in [README.md](README.md).

Architecture details stay in `AUTOSEQ_ARCHITECTURE.md` and `AUTOSEQ_INACTIVE_QUEUE.md`. Extract/style/boundaries: [RFC 0002](rfcs/0002-extract-and-boundaries.md). Companion: [RFC 0001](rfcs/0001-ble-companion.md) (Nano UART; phone path not locked, I19). [RFC 0003](rfcs/0003-m32-pocket-port-and-ble-time.md) (Pocket+CTS bundle) is **rejected**. B15 CTS is ROADMAP-only; I17 gets its own RFC if sequenced. Long features get an RFC; this file only points at them.

Ship on `origin/main`. Talk through changes before a local commit (see [README.md](README.md)). Do not open `upstream` PRs unless explicitly asked.

| I28 | Headless web application: the phone as the only UI ([RFC 0004](rfcs/0004-headless-web-architecture.md)) | **Designed 2026-09-10 and sequenced to Now the same day, succeeding I3. I28a is largely built** — the framed Port A codec, the host event stream, the browser log viewer and browser clock sync have all shipped — **but its Done-when is not met: no TX command crosses the link yet.** Delivery infrastructure (I28b, I28c) started 2026-09-12 in parallel with that remainder; see the sequencing note below. Every operator-reachable function leaves the device and arrives in a browser. The load-bearing idea is an inversion: the browser is the internet-connected device and the sidekick is a local peripheral, so QRZ, PSKReporter and map tiles are the phone's problem and never the radio's — and taken to its conclusion the sidekick **never speaks TLS at all**, because the browser fetches bundles over TLS and relays them onward over plain LAN. That deletes the CA bundle, its rotation and its expiry (~116 KB of flash, measured), and closes all three decisions RFC 0001 §5.2d left open: CA maintenance stops existing, bootstrap beats a full embed, and **unsigned images are the accepted answer** — the browser's own TLS session already authenticates the source one hop earlier, so what the device is actually missing is authorization on the LAN, which is I28b. **Three constraints fixed the shape.** (1) *Offline field operation is required* — a summit has no cell service, so the app is served by the sidekick rather than the internet; mixed-content rules mean an internet-hosted page could not reach `http://minift8.local` anyway, since browsers block active mixed content with no exception for private addresses. (2) *Internet may be required for first setup*, which is what makes it affordable to keep the app out of firmware — a sidekick that has never had internet can provision WiFi and accept a bundle, and nothing more. (3) *Nothing may depend on the ADV's screen or keyboard*, so the protocol is specified against the application, not the board, and a P4 build and an ADV build present the same surface. Does not cover the P4 port itself ([I27](ROADMAP.md), gated on B26) and does not remove the ADV's existing UI. **Sequencing is not optional: I28a gates the application.** The app is the visible half; the protocol is the half that makes it possible, and starting the app first is the one error this design invites — RFC 0004's Ask says so explicitly. **Narrowed 2026-09-12 from "gates everything else", as an explicit decision rather than a drift:** the delivery chain (I28b pairing, I28c partition and bootstrap) shares no code with the Port A link — it is CI plus the sidekick's WiFi/HTTP side — so it runs in parallel, the way B47's transport trial already does, and the partition change is cheapest while exactly one device exists. What stays gated behind I28a is I28d. Transport for I28a is deliberately undecided ([B47](ROADMAP.md)) and must not block it: framing does not assume a stream, so UART and I2C stay swappable. Slices: **I28a — sidekick-to-main protocol.** Framed, bidirectional, transport-agnostic messages across Port A: decodes out at slot cadence, commands in, config and log. Port A carries a version beacon today and must keep coexisting with `main/porta.cpp`'s `PortaRole` arbitration. A full slot of decodes is roughly 3 KB, so throughput is a couple of hundred bytes per second; commands want low latency, decodes tolerate hundreds of ms. Done-when: the ADV streams live decodes to a test client and accepts a TX command over the link, with the ADV's own screen unused. **I28b — control API and pairing token.** The API surface, plus a token minted at provisioning and held by the browser. Without it any device on the LAN can key the transmitter and the licensee answers for it. It guards transmit control, the bundle POST, the firmware OTA POST and every config write — including the bundle-host URL, and including the browser clock sync, which is a write even though an idempotent and self-correcting one. **Reads are open on principle, settled 2026-09-12:** anyone may listen to amateur transmissions on licensed spectrum and Part 97 forbids obscuring a transmission's meaning in the first place, so a decode has nothing to protect and a design that hid one would be at odds with the service it serves. That replaces a weaker reason — "so a second device can watch" — which described the same behaviour but invited a later change trading it away for tidiness; it also retires the idea of a read-scoped second token, since a watch-only guest needs no credential at all. The one carve-out is that **a credential is not radio data**, so a read handing back the WiFi password or the token itself stays guarded. That carve-out is why route policy is a required argument where each route is registered rather than a rule derived from the HTTP method: "GET is open" is right for every route today and silently wrong for the first one that returns a secret, and requiring the argument makes an undeclared route a build error instead of an omission. Known limit, recorded so it is not later mistaken for a defect: the token travels in clear over plain HTTP and is replayable by anyone who can read the traffic, which WPA2/WPA3 makes materially harder and an open network does not — a nuisance control, not a targeted-attacker one. **Moved ahead of the partition slice 2026-09-12, and it is now the whole of the security design.** **Retrieval is part of this slice, because enforcement without a way to read the token is a trap:** the token lives in browser `localStorage`, and needing it again is ordinary rather than catastrophic — a second device, a new phone, cleared browsing data, or Safari's ITP evicting storage for a site untouched for seven days, which a monthly-used sidekick hits with no user action. So the AtomS3 Lite's user button opens a short disclosure window: press it and a route serves the token; the first successful GET claims and closes it (timeout if unclaimed). Every page loads `/pairing.js`, which polls for that claim — no copy-paste. The NVS token is not rotated on retrieval. GPIO41, plain input on the board's own pull-up, active low, read out of the vendored `M5Unified` rather than guessed. One gesture covers everything, since with the token in hand the guarded `/forget` is reachable — so no long-press, no boot-count trigger, no NVS reset path. **Gating disclosure on the button rather than on AP mode is the load-bearing choice**, not a detail: AP-mode gating was the obvious design and [B55](ROADMAP.md) rules it out, because if the app runs over AP mode then "disclosed only in AP mode" means disclosed during normal operation. A button is physical in both modes, and the operator never has to leave their network to pair a second device. Done-when: an unpaired browser can watch and cannot transmit. Open: two paired browsers, one transmitter. **Signing: examined 2026-09-12 and rejected, not deferred** (RFC 0004 §4 carries the argument). Both this row and RFC 0004 §9 previously sequenced a signing chain here. It is redundant rather than merely expensive: step 2 of the delivery path is an HTTPS fetch the browser validates against the public CA system, so the source is already authenticated one hop before the device sees it, and because §2 means the device never speaks TLS there is no path where content arrives other than by relay through the operator's own browser. A CI-held key would also share the GitHub account's trust domain — any workflow can use a secret and anyone who can push a workflow can exfiltrate it — so whoever could serve a hostile bundle could sign it. Against that it costs a pinned key with no revocation path for the life of every device. What was actually missing was authorization on the LAN, which is this slice. Reopen when content can reach a device by a path that is not the owner's browser: sidekicks distributed to other operators, or an unattended update path. **I28c — app partition and bootstrap.** Partition at the 1.9 MB free tail above `ota_1`, `nvs` untouched; token-guarded phone-relayed POST; per-asset SHA-256 in the manifest to catch a truncated upload (corruption, not adversaries — whoever supplies the bundle supplies the manifest); assets stored pre-compressed and served `Content-Encoding: gzip`; manifest pairs bundle to API version and the sidekick refuses a bundle it cannot serve, saying so plainly. No bundled map tiles, no heavyweight framework — 100-300 KB gzipped is the budget. **The bundle host is a requirement list, not a vendor:** HTTPS with a publicly-trusted certificate, and a CORS header permitting a plain-HTTP origin to read the response. GitHub Pages is the implementation and was measured 2026-09-12 to send `Access-Control-Allow-Origin: *` on a plain `GET` from an `http://minift8.local` origin; it answers a preflight with 405, so the fetch stays a simple request with no custom headers, and GitHub Releases assets (where CI publishes firmware today) send no such header and cannot carry the bundle. CORS here is a capability question, not a security one — the browser is the courier and a courier must be able to read the parcel. Base URL lives in **NVS with a build-time default**, so a provider swap is a config change rather than a reflash; that measurement is the gate on any new host. Done-when: a factory sidekick receives an app from a phone and serves it after a power cycle with no internet present. **Log routing (part of I28a's event stream, recorded so it is not lost).** The ADV's `debug_log_line()` output travels to the sidekick as `EVENT(log)` and is printed on the sidekick's USB-C, which is idle exactly when the ADV's own USB-C is busy hosting the radio. This replaces the G4/G5 console removed with `gnss_lora` -- moved, not dropped -- and it is not optional for headless: on a P4 build there is no screen, so `P` then `.` does not exist and this is the only log. Three constraints: route the curated `debug_log_line()` stream rather than raw `ESP_LOG`, whose boot output alone would starve a ~11 KB/s link shared with control traffic; make log events **droppable** through a bounded queue, because the producer is the slot loop and a missed TX window costs more than a missed line; and note it cannot diagnose its own transport -- if PORTA is down there are no logs saying so, which is why the on-screen log stays the fallback wherever a screen exists.
**Pages are files, not string literals (2026-09-12).** Groundwork shared by I28c and I28d, done while the bootstrap pages were still small enough to move cheaply. Every page the sidekick serves is now a `.html` file under `sidekick/main/web/`, embedded with `EMBED_TXTFILES` and interpolated with `{{name}}` placeholders instead of `snprintf`. The reason is not tidiness: CSS written as `width:100%%` to survive `snprintf` put every page beyond a formatter, a validator or a browser, and a page's JavaScript could not be checked for a syntax error at all. It also closed a live hole — the status page interpolated the stored SSID raw, and an SSID is whatever a nearby access point broadcast rather than the operator's own text, so a network named with a `<script>` tag executed on the origin that holds the pairing token. Substitution escapes by default and passing markup through takes an explicit flag. Now a repo rule (`STYLE.md`), because I28d's app is where the temptation to concatenate markup in C would otherwise return at scale.
**I28d — the application.** QRZ is called **directly from the browser** (B48): each operator's credentials go from their own browser to QRZ and never touch our infrastructure, which removes the one-subscription-serves-everyone problem rather than working around it. A refused QRZ lookup must read as a missing optional service, never a fatal error — that CORS header is observed behaviour, not policy. PSKReporter needs a Cloudflare Worker that holds no credentials and **filters rather than relays**: one measured query returned 1.25 MB of XML, which is not something to hand a phone on cellular every refresh. Google Maps needs no proxy; its key ships in a static app and must be referrer-restricted. Done-when: a QSO is completed end to end from a phone with the ADV's screen unused. |

| B53 | Decode instrumentation: one line per slot (gates B54 and I26) | **Scoped 2026-09-12 from a desk audit of the decode path, verified against `1ffcd6b`; not built.** Five numbers, one log line per slot, on the existing public log path (`debug_log_line_public()`) so it is readable with the radio plugged in — `P` then `.`, and the browser viewer. **Three of the five are already computed and thrown away.** `slot_blocks` and `wf.num_blocks` are already logged at every slot boundary by the `"Slot boundary"` `ESP_LOGD` in `ft8_audio_pipeline_run()`, at a level `CONFIG_LOG_MAXIMUM_LEVEL=3` compiles out of the image; `num_candidates` and `s_dec_count` are live in `decode_monitor_results()`. Only decode wall-time (two `rtc_now_ms()` calls around that function's candidate loop) and the sample-arrival deficit (accumulate `cfg->read`'s return against 90,000 samples per 15 s slot) are new. Proposed line: `SLOT g=14 lost=0ms dec=340ms cand=23/50 msg=8/32`. **`slot_blocks` is diagnostic because it resets twice** — at the slot boundary and again after a decode — so the count printed at a boundary is the guard band that survived decode: ~14 blocks is healthy (93 per slot minus 79 consumed), ~0 means decode ate the guard, and a boundary reached with fewer than 79 and no decode at all means the audio never arrived. **Do not read it by raising `CONFIG_LOG_MAXIMUM_LEVEL` globally** — that compiles in every `ESP_LOGD` in the tree, and the resulting flood is its own starvation source, corrupting the measurement it is meant to take; it also needs the G4/G5 UART adapter, since the radio owns USB-C. Seam: the guard count lives in the pipeline and the candidate/decode counts in `main.cpp`, so one line means a small shared struct — `decode_tx_state.h` already holds cross-file decode state. **Done-when: a field run on a busy band, FT8 and FT4 both, produces the line and it reads either healthy (`lost`≈0, `g`≈14, `dec` well under 2360 ms) or sick (`lost` non-zero and tracking `dec`, `g` collapsing toward 0 on high-`cand` slots).** Either answer closes the question B54 is gated on. FT4 is the sharper test: near-identical guard (2.46 s against FT8's 2.36 s) but 105 symbols to decode instead of 79, and its decode already needs a 16 KB task stack against FT8's 8 KB (the FT4 branch of the `stream_uac` task create). `cand=` carries a second, independent payload: if a busy evening never approaches 50, I26's `num_candidates` lever buys nothing and drops off the list before a session is spent on it. |
| B54 | Decode capture path: USB audio starvation and single-buffered capture | **Desk-audited 2026-09-12 against `1ffcd6b`, unmeasured on hardware — gated on B53.** Two coupled defects in the path that *feeds* the decoder, distinct from I26, which tunes the decoder itself. Different gate, too: I26 waits on a host harness (B25); this waits on a field measurement no host harness can take. **(a) There is no app-side buffer between USB and the decoder.** `uac_read_ft8_samples()` calls `uac_host_device_read()` straight through and resamples inline; the only ringbuffers under `main/audio/` are the driver's own and the TX speaker's. Total queue depth is `UAC_BUFFER_SIZE` 4000 B = **13.9 ms** at 288 B/ms (48 kHz / 24-bit / stereo), with reads of `UAC_READ_BUFFER_SIZE` 2304 B = 8 ms. **The loss is silent by construction, and that is confirmed in our own vendored driver rather than inferred.** On ring-full the driver discards the whole transfer with one `"RX Ringbuffer overflow"` `ESP_LOGD` in `managed_components/espressif__usb_host_uac/uac_host.c` that our build level compiles out. Its one near-overflow signal, `UAC_HOST_DEVICE_EVENT_RX_DONE`, is queued as `UAC_EVT_DEVICE` by `uac_device_callback()` and never consumed — the `uac_lib_task` event loop handles only `UAC_EVT_STOP` and `UAC_EVT_DRIVER` — and it would be useless anyway, because the same driver also fires it every time the ring passes `ringbuf_threshold` (600 B), i.e. constantly. **There is no countable overflow signal in this driver**, which is why B53 measures the deficit app-side instead. **(b) Capture is single-buffered and decode runs in the capture task.** `ft8_audio_pipeline_run()` holds one `monitor_t` and one `ft8_buffer` and calls `decode_monitor_results()` inline; after decode it resets the monitor and restarts pacing from now, so whatever decode took is audio that was dropped at the wire while it ran. The budget is the guard band: FT8 is 79 symbols × 0.160 s = 12.64 s of signal in a 15 s slot, leaving **2.36 s**; FT4 is 105 × 0.048 = 5.04 s in 7.5 s, leaving **2.46 s**. Exceed it and we clip the opening sync of the next slot. **Our deliberate skip of decode on our own TX slot (the `g_tx_active \|\| g_was_txing` branch) is not this** — that is the slot we were transmitting in, which we could not hear anyway. **A constraint on the obvious fix, worth writing down before someone trips it:** `uac_read_ft8_samples()` discards its `max_samples` argument (`(void)max_samples;`) and writes into a 512-float `temp_dec`, so at 6 B/frame and 8:1 decimation the implicit ceiling is `UAC_READ_BUFFER_SIZE` ≤ 24,576 B. Nothing today approaches it; growing the read buffer past it overruns silently. **Done-when: B53's field run says whether either defect is real here.** If `lost`≈0 and `g`≈14 on a busy band, both close as answered and I26 proceeds uncoupled. If not, the fixes are an app-side ring deep enough to cover decode, and moving decode off the capture task — in that order, one at a time, measured per `TEST_PLAN.md`'s decode-yield protocol. |

The symptom is indirect and nasty: plugged in, the battery percentage *falls*, because the device runs from the pack while the charger supplies nothing. It is worse still with the side switch off, which isolates the pack and leaves the divider reading the charger rail -- a confident **100%** that means nothing. Both readings sent the operator looking for a firmware bug that was not there. **Why a PD source might refuse:** a USB-C source only enables VBUS once the sink advertises itself through CC pull-downs, where a USB-A port has VBUS live unconditionally. | B47 | Sidekick transport: keep PORTA UART, or move to I2C | **Deliberately deferred 2026-09-10 — recorded so the protocol work does not silently assume UART.** The sidekick link is a UART on Grove G1/G2 today. The alternative is I2C on the same two wires, and the case for it is multi-drop rather than speed: **Port A is the I2C port by M5Stack convention**, so a UART there is the non-standard choice and is why none of M5Stack's Grove catalogue can share the port with the sidekick. The strongest evidence is already in this repo — `main/porta.cpp`'s `PortaRole` state machine, arbitrating Port A between a GPS and the companion with a silence timeout, exists *only because UART makes the port exclusive*. On I2C that whole mechanism dissolves into addresses. **Bandwidth does not decide it:** a full slot of decodes is roughly 3 KB per 15 s — a couple hundred bytes per second, bursty — against ~10 KB/s for 100 kHz I2C and ~11 KB/s at 115200 baud, both enormous overkill, so choose on properties. **The master/slave asymmetry happens to fall the right way.** Grove carries 5V, GND and two signals, so there is no spare pin for a data-ready interrupt and the sidekick (as master) must poll — but commands travel browser -> sidekick -> radio and are master-initiated, so they are immediate, while decodes travel the other way on a 15 s boundary where a 5 Hz poll is invisible. Polling is bad at exactly the thing this link does not have. **Three risks, in the order they deserve worry:** (1) the main MCU becomes an I2C *slave*, and ESP-IDF's slave support has historically been the weak half of that driver — IDF 5.x has a newer one, and whether it is solid for sustained use needs proving rather than assuming; (2) bus wedging — a slave stuck holding SDA low takes the bus down until something clocks it free, on a connectorised cable that gets plugged and unplugged in the field, where UART has no equivalent failure because a corrupt byte is just a corrupt byte and the next frame resyncs; (3) cable capacitance, fine at Grove lengths and worse than UART if the cable ever grows. **Must not become a blocker:** the sidekick/main protocol is to be specified as framed messages over a byte pipe, with framing that does not assume a stream, so the transport stays a swappable layer and the app, the control API and the protocol design do not depend on which wins. Shaped like B26 — an experiment with a real answer either way, not an argument. Done-when: on hardware, an ESP32-S3 sustains our traffic pattern as an I2C slave for a full unattended beacon run without a stall, and the bus recovers on its own from a live cable disconnect and reconnect; if either fails, PORTA UART stays and this row closes as answered. |

The reason is structural rather than incidental: **`libft8_lib.a` alone is 108,212 B of DIRAM, 44% of the 247 KB used** — the decoder *is* the memory hog, so freeing memory *around* it will always be marginal. kgoba's demo default (t2/f2) is simply not reachable on this silicon; t2/f2 plus OSD would be ~322 KB. **But an equal-cost swap exists and is the actual near-term target:** because the product is `time_osr x freq_osr`, **`t=1, f=2` costs exactly the same 80,538 B as today's `t=2, f=1`** — same arena, zero allocation change. It trades time resolution for frequency resolution instead of buying both. CPU looks near-neutral (today: 2 FFTs of nfft=960 per block; then: 1 FFT of nfft=1920 — ~2.1 vs ~2.0 units at O(n log n)), but `nfft` doubling pushes kiss_fftr past the 12,288 B static arena into a ~20 KB `malloc`, so that arena needs ~8 KB more BSS to stay static. Both need measuring against the ~13 s slot budget. Whether the swap *helps recall* is unknown and unknowable without the harness — which is the point: **build the recall harness first, then A/B `t2/f1` vs `t1/f2` at zero memory cost.** Do not write a roadmap target of "get to freq_osr=2"; that target is unreachable on ESP32-S3 and the reachable experiment is the swap. **Slower RAM is a sound idea that fails on hardware, not on principle (2026-09-04):** RFC 0001 §2's PSRAM non-goal is about **DMA buffers** and has been read too broadly — the waterfall is plain CPU-swept data, never a DMA target, so it would be a legitimate `EXT_RAM_BSS_ATTR` / `MALLOC_CAP_SPIRAM` candidate (subject to measuring candidate-search sweep cost) on a board with PSRAM. Neither board this project owns has any: confirmed on hardware 2026-09-04 via `esptool.py flash_id` — Cardputer ADV (Stamp-S3A) and AtomS3 Lite both report `Features: WiFi, BLE, Embedded Flash 8MB` with **no** `Embedded PSRAM` (see RFC 0001 §2 for the full readings). The AtomS3 Lite was checked deliberately, not incidentally: had *it* carried PSRAM, headless-on-Atom (I24) would have been the cheapest route to `freq_osr`=2 on hardware already in hand and would have reordered this entry. It does not. See RFC 0001 §2 and I24 for the PSRAM-class host that would lift the ceiling outright. **Verified against `1ffcd6b` 2026-09-12; cite by symbol, not by line — the two line numbers this row used to carry had both rotted by then.** Current values by symbol: `g_freq_osr`=1 and `g_time_osr`=2 in `main/main.cpp`; `max_cand`=50 and the `min_score` argument 5 on the `ftx_find_candidates()` call in `decode_monitor_results()`; `max_iterations` 25 on that function's `ftx_decode_candidate()` call; `DEC_MAX`=32 via `RX_MAX_DECODES` in `components/ui/include/ui.h`. kgoba's demo defaults, read directly from the `k*` constants at the top of `components/ft8_lib/vendor/demo/decode_ft8.c`: `kMin_score`=10, `kMax_candidates`=140, `kLDPC_iterations`=25, `kMax_decoded_messages`=50, `kFreq_osr`=2, `kTime_osr`=2. **So we are below kgoba on exactly two of six** — `freq_osr` and `num_candidates` — and this row's existing claim that `min_score` and `max_iterations` match or beat upstream is confirmed: our `min_score`=5 is *more* permissive than his 10, and 25 iterations is his number exactly. **`DEC_MAX`=32 is the cheapest item here and is not a DSP limit at all**: the candidate loop stops at `s_dec_count < DEC_MAX`, so a busy slot is truncated by the size of the RX list, not by the decoder. The separate `kMaxDecoded`=50 sizing the payload-dedupe hashtable already matches kgoba. **Whether any of these bind in the field is the `cand=`/`msg=` half of B53** — raising `num_candidates` against a band that never reaches 50 buys nothing. **One external data point on the `freq_osr` ceiling this row proves unreachable on S3:** an independent FT8 decoder project built on this same `ft8_lib` base runs `freq_osr`=2 in production on an ESP32-P4-class part, which makes the ceiling a measured practical loss rather than a theoretical one. That is I27's argument, not a reason to re-run the S3 arithmetic. **Two hypotheses in the audio path, both host-testable once B25 exists, neither a finding:** (1) *Per-block AGC.* `ft8_audio_pipeline_run()` normalises every block to a target mean with gain clamped to [0.1, 10] before `monitor_process()`; WSJT-X has no equivalent step. The block is one full FT8 symbol (`block_size` in `monitor_init()` is `sample_rate * symbol_period` = 960 samples at 6 kHz), not a fraction of one, so a per-block scalar cannot compress the strong-to-weak ratio *within* a block — it multiplies every bin equally. What it changes is the time axis: consecutive symbols get different gains, so a steady signal acquires an artificial envelope as other stations key up at their own offsets. It is probably **load-bearing rather than vestigial**, since `monitor_process()` quantises to 8 bits over a fixed -120..0 dB window and without a level normaliser a quiet band floors while a loud one clamps — removing it is not free. It also makes reported SNR relative to a moving reference, since the noise floor is a percentile over the already-normalised waterfall. (2) *Unfiltered decimation, and this is the larger suspect.* `resample_48k_to_6k()` is bare 8:1 stride with no anti-alias filter, justified in-code by "input is already bandwidth-limited". If the QMX passes anything above 3 kHz it folds into the passband and raises the noise floor, which costs weak decodes directly; WSJT-X filters before decimating. **This constrains B25's corpus format:** record at 48 kHz tapped at the USB wire, or the aliasing is already baked in and neither hypothesis is testable. |
