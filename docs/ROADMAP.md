# Mini-FT8 roadmap (kb2slo fork)

Living plan for this fork. How to use it, and the rest of `docs/`, is in [README.md](README.md).

Architecture details stay in `AUTOSEQ_ARCHITECTURE.md` and `AUTOSEQ_INACTIVE_QUEUE.md`. Extract/style/boundaries: [RFC 0002](rfcs/0002-extract-and-boundaries.md). Companion: [RFC 0001](rfcs/0001-ble-companion.md) (Nano UART; phone path not locked, I19). [RFC 0003](rfcs/0003-m32-pocket-port-and-ble-time.md) (Pocket+CTS bundle) is **rejected**. B15 CTS is ROADMAP-only; I17 gets its own RFC if sequenced. Long features get an RFC; this file only points at them.

Ship on `origin/main`. Talk through changes before a local commit (see [README.md](README.md)). Do not open `upstream` PRs unless explicitly asked.

| B24 | On-demand USB host (retire always-on) + decide presence | B18 (`80b9ebe`, 2026-09-02) installs the USB host at boot unconditionally (`uac_host_ensure_started()`, main.cpp:4993) and never releases it until something asks. The justifications were correctness (`C`), matching the intended design, and freeing the block during the idle state CTS actually uses. **Reprioritised 2026-09-04:** B23 removes USB Drive, so the `C` justification is gone. | I24 | Headless Atom+Nano host, single binary with ADV+Nano | Northstar: one Mini-FT8 binary runs on Cardputer ADV+Nano (LCD/keyboard UI) or an Atom (M5Stack AtomS3-family)+Nano (headless, gracefully degraded, no LCD/keyboard). **Closed as scoped, hardware-confirmed 2026-09-05:** "an Atom (M5Stack AtomS3-family)" was never bench-tested as a QMX USB host until now — it just failed. Two threads, not one, now: (a) a board on the ADV's own **Stamp-S3A module** (screen/keyboard-less) would inherit the ADV's already-proven host behavior outright, but none has been sourced standalone; (b) the more actively pursued thread has shifted to a **different chip**, ESP32-P4, for the decode-headroom reasons below — it does *not* inherit S3's proof and needs its own bench test, now tracked as B26. Its real payoffs are ~80 KB of *flash*, and being the portability seam for a PSRAM-class host — not DIRAM for I26's waterfall, which is short by ~67 KB. Do not sequence this expecting it to buy decode depth. Needs a UI/board abstraction ahead of today's Cardputer-only `main.cpp`/`M5Cardputer` coupling — likely intersects B14 (radio profile table) and I6 (multi-mode/mode-agnostic core). **Done-when addition 2026-09-04 (non-negotiable):** headless must have a working log-offload path before it ships. The AtomS3 Lite has no SD card and B23 removes USB Drive, so a headless host has *no* local way to get `.adi` files out unless one is built. The designed answer is the Nano USB-C CDC log bridge (RFC 0001 §5.1: "USB-C CDC for desk flash and optional ADV-log bridge") — ADV → PORTA UART → Nano → the Nano's own USB-C as plain CDC. It is cheap (no lwIP/AP/DHCP), avoids OTG device mode entirely, and the Nano is present in every headless configuration by definition. It is also **unbuilt**. Do not treat it as an assumption: if this lands without it, headless cannot offload logs at all, which is a worse failure than the one B23 removes. Explicitly do not substitute I19 here — that is unmeasured with its own fail conditions. Not scheduled; own RFC before code once sequenced. **Future consideration (2026-09-04):** the same UI/board abstraction this needs would also make an ESP32-P4-based headless host viable later — not a separate porting project, since headless mode by definition has no display/keyboard dependency to carry over. P4 has no built-in WiFi/BLE (Espressif's own ESP-Hosted/ESP-AT pattern pairs it with a companion radio chip over SDIO/SPI/UART); M5Stack's own Stamp-P4 + Stamp-AddOn-C6-For-P4 (dedicated BTB connector, part `HC-PBB40C-20DS-0.4V-2.5-02`) is the closest off-the-shelf realization of that pattern, and M5Stack's Tab5 (P4 + ESP32-C6-MINI-1U over SDIO) is a real, shipping product proving the pairing works. Verified specs (docs.m5stack.com, checked 2026-09-04): P4 dual-core RISC-V up to 360-400MHz vs our current S3's 240MHz, plus up to 32MB Octal PSRAM vs the S3's on-chip SRAM only — directly relevant to I26's DIRAM/PSRAM ceiling for OSD-class decode work. Not pin/footprint compatible with the ADV's existing Stamp-S3A (29.8×22.0mm vs 26.0×18.0mm, 44 GPIOs vs 23) — no drop-in retrofit; this is a bare-module/custom-carrier path if pursued. No M5Stack Cardputer-line product on P4 exists as of this writing. Tab5 would be the fastest way to bench-validate an actual decode-performance win before committing to any of this. **Decode headroom quantified 2026-09-04 (see I26):** the mechanism is on-chip SRAM, **not** clock and **not** PSRAM. P4's 768 KB SRAM vs the S3's 512 KB (~94 KB DIRAM remaining at link) moves `freq_osr`=2 at `time_osr`=2 from impossible (needs 161 KB) to unremarkable, and puts OSD's ~322 KB class within reach for the first time. Two cautions: the 32 MB PSRAM is **not** the win — the waterfall is swept repeatedly during candidate search, and Octal PSRAM behind a cache is far slower than on-chip SRAM, so parking it there could be slower than today despite a 1.5x core; PSRAM's value is holding cold data so SRAM stays free for the decoder. And 360 vs 240 MHz alone would not have justified a move. The ~7pt recall figure remains Web-888's on Zynq7010, never measured on P4 and never measured for Mini-FT8 — so this is well-founded as *headroom* and entirely unquantified as *recall* until I26's harness exists. Not scheduled, no RFC — noting the option here so it isn't lost. |

Call it ~25 KB against a ~67 KB shortfall. It does not close. The reason is structural rather than incidental: **`libft8_lib.a` alone is 108,212 B of DIRAM, 44% of the 247 KB used** — the decoder *is* the memory hog, so freeing memory *around* it will always be marginal. kgoba's demo default (t2/f2) is simply not reachable on this silicon; t2/f2 plus OSD would be ~322 KB. **But an equal-cost swap exists and is the actual near-term target:** because the product is `time_osr x freq_osr`, **`t=1, f=2` costs exactly the same 80,538 B as today's `t=2, f=1`** — same arena, zero allocation change. It trades time resolution for frequency resolution instead of buying both. CPU looks near-neutral (today: 2 FFTs of nfft=960 per block; then: 1 FFT of nfft=1920 — ~2.1 vs ~2.0 units at O(n log n)), but `nfft` doubling pushes kiss_fftr past the 12,288 B static arena into a ~20 KB `malloc`, so that arena needs ~8 KB more BSS to stay static. Both need measuring against the ~13 s slot budget. Whether the swap *helps recall* is unknown and unknowable without the harness — which is the point: **build the recall harness first, then A/B `t2/f1` vs `t1/f2` at zero memory cost.** Do not write a roadmap target of "get to freq_osr=2"; that target is unreachable on ESP32-S3 and the reachable experiment is the swap. **Slower RAM is a sound idea that fails on hardware, not on principle (2026-09-04):** RFC 0001 §2's PSRAM non-goal is about **DMA buffers** and has been read too broadly — the waterfall is plain CPU-swept data, never a DMA target, so it would be a legitimate `EXT_RAM_BSS_ATTR` / `MALLOC_CAP_SPIRAM` candidate (subject to measuring candidate-search sweep cost) on a board with PSRAM. Neither board this project owns has any: confirmed on hardware 2026-09-04 via `esptool.py flash_id` — Cardputer ADV (Stamp-S3A) and AtomS3 Lite both report `Features: WiFi, BLE, Embedded Flash 8MB` with **no** `Embedded PSRAM` (see RFC 0001 §2 for the full readings). The AtomS3 Lite was checked deliberately, not incidentally: had *it* carried PSRAM, headless-on-Atom (I24) would have been the cheapest route to `freq_osr`=2 on hardware already in hand and would have reordered this entry.
