# Mini-FT8 roadmap (kb2slo fork)

Living plan for this fork. How to use it, and the rest of `docs/`, is in [README.md](README.md).

Architecture details stay in `AUTOSEQ_ARCHITECTURE.md` and `AUTOSEQ_INACTIVE_QUEUE.md`. Extract/style/boundaries: [RFC 0002](rfcs/0002-extract-and-boundaries.md). Companion: [RFC 0001](rfcs/0001-ble-companion.md) (Nano UART; phone path not locked, I19). [RFC 0003](rfcs/0003-m32-pocket-port-and-ble-time.md) (Pocket+CTS bundle) is **rejected**. B15 CTS is ROADMAP-only; I17 gets its own RFC if sequenced. Long features get an RFC; this file only points at them.

Ship on `origin/main`. Talk through changes before a local commit (see [README.md](README.md)). Do not open `upstream` PRs unless explicitly asked.

| I28 | Headless web application: the phone as the only UI ([RFC 0004](rfcs/0004-headless-web-architecture.md)) | **Designed 2026-09-10, not started. Sequenced to Now the same day; I3 shipped and this succeeds it.** Every operator-reachable function leaves the device and arrives in a browser. The load-bearing idea is an inversion: the browser is the internet-connected device and the sidekick is a local peripheral, so QRZ, PSKReporter and map tiles are the phone's problem and never the radio's — and taken to its conclusion the sidekick **never speaks TLS at all**, because the browser fetches signed bundles and relays them over plain LAN while the device verifies a pinned public key. That deletes the CA bundle, its rotation and its expiry (~116 KB of flash, measured), and settles two of the three decisions RFC 0001 §5.2d left open. It forces the third: signing stops being optional, because it is what replaces TLS as the source of trust. **Three constraints fixed the shape.** (1) *Offline field operation is required* — a summit has no cell service, so the app is served by the sidekick rather than the internet; mixed-content rules mean an internet-hosted page could not reach `http://minift8.local` anyway, since browsers block active mixed content with no exception for private addresses. (2) *Internet may be required for first setup*, which is what makes it affordable to keep the app out of firmware — a sidekick that has never had internet can provision WiFi and accept a bundle, and nothing more. (3) *Nothing may depend on the ADV's screen or keyboard*, so the protocol is specified against the application, not the board, and a P4 build and an ADV build present the same surface. Does not cover the P4 port itself ([I27](ROADMAP.md), gated on B26) and does not remove the ADV's existing UI. **Sequencing is not optional: I28a gates everything else.** The app is the visible half; the protocol is the half that makes it possible, and starting the app first is the one error this design invites — RFC 0004's Ask says so explicitly. Transport for I28a is deliberately undecided ([B47](ROADMAP.md)) and must not block it: framing does not assume a stream, so UART and I2C stay swappable. Slices, recorded in Done as they land (the I3 pattern): **I28a — sidekick-to-main protocol.** Framed, bidirectional, transport-agnostic messages across Port A: decodes out at slot cadence, commands in, config and log. Port A carries a version beacon today and must keep coexisting with `main/porta.cpp`'s `PortaRole` arbitration. A full slot of decodes is roughly 3 KB, so throughput is a couple of hundred bytes per second; commands want low latency, decodes tolerate hundreds of ms. Done-when: the ADV streams live decodes to a test client and accepts a TX command over the link, with the ADV's own screen unused. **I28b — app partition and bootstrap.** Partition at the 1.9 MB free tail above `ota_1`, `nvs` untouched; phone-relayed POST; assets stored pre-compressed and served `Content-Encoding: gzip`; manifest pairs bundle to API version and the sidekick refuses a bundle it cannot serve, saying so plainly. No bundled map tiles, no heavyweight framework — 100-300 KB gzipped is the budget. Done-when: a factory sidekick receives an app from a phone and serves it after a power cycle with no internet present. **I28c — signing chain.** CI signs bundle and firmware; pinned public key on device; ESP-IDF signed-app verification without full secure boot. **The one piece with no undo** — a compromised key is a supply-chain compromise for every deployed device and this design has no revocation path, so key handling is part of the slice, not an afterthought. Done-when: an unsigned or tampered bundle is refused on hardware. **I28d — control API and pairing.** The API surface, plus a pairing token minted at provisioning and held by the browser. Without it any device on the LAN can key the transmitter and the licensee answers for it; signing protects the supply chain and says nothing about the control channel. Read-only status may stay open. Done-when: an unpaired browser can watch and cannot transmit. Open: two paired browsers, one transmitter. **Log routing (part of I28a's event stream, recorded so it is not lost).** The ADV's `debug_log_line()` output travels to the sidekick as `EVENT(log)` and is printed on the sidekick's USB-C, which is idle exactly when the ADV's own USB-C is busy hosting the radio. This replaces the G4/G5 console removed with `gnss_lora` -- moved, not dropped -- and it is not optional for headless: on a P4 build there is no screen, so `P` then `.` does not exist and this is the only log. Three constraints: route the curated `debug_log_line()` stream rather than raw `ESP_LOG`, whose boot output alone would starve a ~11 KB/s link shared with control traffic; make log events **droppable** through a bounded queue, because the producer is the slot loop and a missed TX window costs more than a missed line; and note it cannot diagnose its own transport -- if PORTA is down there are no logs saying so, which is why the on-screen log stays the fallback wherever a screen exists.
**I28e — the application.** QRZ is called **directly from the browser** (B48): each operator's credentials go from their own browser to QRZ and never touch our infrastructure, which removes the one-subscription-serves-everyone problem rather than working around it. A refused QRZ lookup must read as a missing optional service, never a fatal error — that CORS header is observed behaviour, not policy. PSKReporter needs a Cloudflare Worker that holds no credentials and **filters rather than relays**: one measured query returned 1.25 MB of XML, which is not something to hand a phone on cellular every refresh. Google Maps needs no proxy; its key ships in a static app and must be referrer-restricted. Done-when: a QSO is completed end to end from a phone with the ADV's screen unused. |

| B47 | Sidekick transport: keep PORTA UART, or move to I2C | **Deliberately deferred 2026-09-10 — recorded so the protocol work does not silently assume UART.** The sidekick link is a UART on Grove G1/G2 today. The alternative is I2C on the same two wires, and the case for it is multi-drop rather than speed: **Port A is the I2C port by M5Stack convention**, so a UART there is the non-standard choice and is why none of M5Stack's Grove catalogue can share the port with the sidekick. The strongest evidence is already in this repo — `main/porta.cpp`'s `PortaRole` state machine, arbitrating Port A between a GPS and the companion with a silence timeout, exists *only because UART makes the port exclusive*. On I2C that whole mechanism dissolves into addresses. **Bandwidth does not decide it:** a full slot of decodes is roughly 3 KB per 15 s — a couple hundred bytes per second, bursty — against ~10 KB/s for 100 kHz I2C and ~11 KB/s at 115200 baud, both enormous overkill, so choose on properties. **The master/slave asymmetry happens to fall the right way.** Grove carries 5V, GND and two signals, so there is no spare pin for a data-ready interrupt and the sidekick (as master) must poll — but commands travel browser -> sidekick -> radio and are master-initiated, so they are immediate, while decodes travel the other way on a 15 s boundary where a 5 Hz poll is invisible. Polling is bad at exactly the thing this link does not have. **Three risks, in the order they deserve worry:** (1) the main MCU becomes an I2C *slave*, and ESP-IDF's slave support has historically been the weak half of that driver — IDF 5.x has a newer one, and whether it is solid for sustained use needs proving rather than assuming; (2) bus wedging — a slave stuck holding SDA low takes the bus down until something clocks it free, on a connectorised cable that gets plugged and unplugged in the field, where UART has no equivalent failure because a corrupt byte is just a corrupt byte and the next frame resyncs; (3) cable capacitance, fine at Grove lengths and worse than UART if the cable ever grows. **Must not become a blocker:** the sidekick/main protocol is to be specified as framed messages over a byte pipe, with framing that does not assume a stream, so the transport stays a swappable layer and the app, the control API and the protocol design do not depend on which wins. Shaped like B26 — an experiment with a real answer either way, not an argument. Done-when: on hardware, an ESP32-S3 sustains our traffic pattern as an I2C slave for a full unattended beacon run without a stall, and the bus recovers on its own from a live cable disconnect and reconnect; if either fails, PORTA UART stays and this row closes as answered. |
| B44 | Sidekick updates: pull over WiFi, not push over PORTA (RFC 0001 §5.2d) | **Designed 2026-09-09, not built.** Amendment written after B42 showed the ROM bootloader cannot be reached over Grove on any of these chips — it only accepts a download session on UART0's default pads (GPIO43/44 on S3, GPIO16/17 on C6), and Grove is GPIO1/GPIO2. That left the custom second-stage bootloader as the only PORTA push path, which is real bootloader engineering whose blast radius is every boot. **Dropped in favour of the sidekick fetching its own firmware**, which its WiFi-plus-browser purpose (§5.0) already requires: `esp_https_ota()` against a manifest, versus a bespoke push protocol with framing, ACKs, baud negotiation and cross-device rollback. Grounded in measurement, not estimate (ESP-IDF 5.5.1, esp32s3): sidekick today 224 KB, IDF `http_server/simple` 795 KB, IDF `simple_ota_example` 911 KB — so TLS costs +116 KB and a full sidekick is ~1.2–1.4 MB. Partition change is needed anyway because the current 1 MB `factory` will not hold the web app; layout is `nvs`/`phy_init`/`otadata` + two 3 MB OTA slots on the 8 MB part, `nvs` pinned at `0x9000` so later table changes do not wipe config. Sizing is a two-way door with a physical cost (USB-C reflash via the ADV, no desk computer) whose price scales with fleet size — trivial at one device, expensive after distribution, so pick generously once. Credentials come from a SoftAP provisioning page on the browser UI already being built, not from the ADV over PORTA (which would need `Station.txt` fields and menu space that does not exist). Hosting is GitHub Pages via CI, manifest keyed on the same exact git SHA §5.2b already established. USB-C keeps first-install and broken-app recovery. **Three open decisions named in §5.2d:** recurring CA maintenance, unsigned images, and whether the ADV embeds the full app or a minimal bootstrap. |
| B37 | Beacon time limit and TX watchdog | Beacon now re-fires reliably after `949dbd2` (re-arm after TX and on empty RX slots) and `803e8cf` (cancel the queued CQ on beacon-off), confirmed 2026-09-08 by a 3.6 h unattended run: 544 spotted TX slots, 1,195 receiving stations, no gap over 5 min. **Before those, the defect was an accidental time limit** — the beacon silently died on a quiet band because the CQ was only re-queued at the tail of a successful decode, so nothing bounded an unattended run and nothing needed to. Upstream hit the same bug (`740a898`, "Fix beacon CQ silent on quiet bands") but that commit is not in this fork's ancestry, and it patched only the no-decodes early return, not the after-TX case. Two parts. **(a) Operator-settable beacon duration**, persisted in `Station.txt`, returning `g_beacon` to `OFF` at expiry. **Decided 2026-09-08: wall-clock, not slot count** — wall-clock is what an operator means by "beacon for an hour", at the cost of being less deterministic to host-test than a slot counter. **And a QSO in progress finishes before the beacon stops**, so the limit is deliberately soft; document that on the menu item, since a beacon that keeps transmitting past its stated limit is surprising otherwise. **(b) A broader TX watchdog** — a cap on continuous transmit, or on time without QSO progress — covering the non-beacon paths too. Reuse the existing `board_power_halted()` halt path rather than adding a second way to stop TX. **Menu placement is the blocker:** MENU is full at 18 items across 3 pages, `M`/`N`/`O` address pages 0/1/2 only, and `static_assert(kMenuItemCount == 18)` in `main.cpp` fails the build on a naive 19th item (working as intended — B32 put it there for this). I22 (nested Settings under `M`) is the roadmap's answer and probably sequences first, or this needs its own placement decision. README carries the no-limit caveat in the meantime. |

| B24 | On-demand USB host (retire always-on) + decide presence | B18 (`80b9ebe`, 2026-09-02) installs the USB host at boot unconditionally (`uac_host_ensure_started()`, main.cpp:4993) and never releases it until something asks. Two consequences, both measured 2026-09-04: it holds ~6 KB of the largest contiguous DMA block continuously (44K -> 38K, RFC 0001 §4.1c), and it leaves the OTG core in host mode from power-on, which is why USB Drive (`C`) cannot enumerate (B23). **Do not justify this on memory.** 6 KB does not scale §4.1b's ~40K-class contiguous requirement, so this will *not* unlock B17. The justifications were correctness (`C`), matching the intended design, and freeing the block during the idle state CTS actually uses. **Reprioritised 2026-09-04:** B23 removes USB Drive, so the `C` justification is gone. What remains is the design-intent argument and ~6 KB during idle — which by the same entry's own reasoning does not unlock B17. That is a thin case; treat this as low priority unless CTS work resurfaces it, and do not sequence it as a slimming win. **Hard constraint to decide first:** presence *is* a USB host client (`usb_host_client_register()` in `usb_c_presence_host.cpp`) and there is no VBUS/D+ sense line in firmware or on the board, so boot-time plug/unplug toasts and an on-demand host are mutually exclusive (RFC 0001 §5.5). Either presence becomes implicit (host comes up for **S -> 2**, nano flash, `C`) and toasts are lost, or the host stays up and `C` stays broken. That is a product call, not an implementation detail. Blocked on B23's kill-or-fix decision: if USB Drive is deleted, the `C` half of the motivation goes with it. Done-when: host installs only on demand and releases after; `S -> 2` still streams QMX; nano flash still works; boot **DM L** back to ~44K. Field-only. |
